# Dota Improviser: agents and flow

Stats-only companion. **No** memory reading, input injection, packet sniffing, or hidden-info extraction. Gameplay inputs: Valve GSI (player-visible, opt-in cfg), public OpenDota aggregates, local read-only files (`steam.inf`, `itembuilds/`, Steam `loginusers.vdf`), and picks the user types. For overlay placement only, the main process may use the OS-reported foreground Dota window bounds. One deliberate, narrow, opt-in exception to "no screen scraping" exists — see "Draft vision" below — strictly gated to pick/strategy phase and never used for anything else.

## Draft vision (the screen-reading exceptions)
Off by default (`draftVision` feature, Settings). The ONLY screen-reading code in the app is `src/main/draft-vision.ts`, and every entry point there takes an explicit boolean gate the caller derives from Dota's own GSI feed (`inPickPhase` for the pick-bar reader below, `justDied` for the death snapshot) — each bails out immediately when its gate is false, and the pick-bar reader never runs once a game is live. The pick-bar path captures the Dota window, crops a single thin strip at the top (the pick-bar portraits), and compares each slot against Valve's own small hero icons (already fetched from Steam's CDN for the app's own portrait grid) — never text OCR, never chat/minimap/buildings, never anything outside that strip. A match feeds into the same `applyReveal()` wave-merge GSI picks already use.
- **Death snapshot** (`deathSnapshot` feature, off by default, `captureDeathSnapshot` in the same file) fires at most once per death — gated on your own GSI feed going alive→dead, never on a timer — and hands back exactly one full-frame screenshot of what was already on *your own* screen, shown in the overlay for ~20s then cleared by the main process. No analysis is attempted on it: unlike the hero-portrait matching above, reliably reading arbitrary game state (map position, building icons) from a small, noisy screen region isn't something this can verify works without a live game to test template-matching against, and shipping a guess there would be exactly the kind of made-up "insight" this project avoids. It's a self-review aid, not a data source.
- **Live map/building/vision-state reading was asked for and declined.** Reading tower/Roshan/minimap state live, during an active match, via screen capture was requested and explicitly turned down — not for the CV difficulty (tiny minimap icons are a much harder matching problem than the large, distinct hero portraits above) but because anything that reveals state the game itself withholds (fog of war, hidden enemy position) during a live multiplayer match is map-hacking territory, regardless of local-only intent, and this project's own guardrail (`tests/guard.test.mjs` confining `desktopCapturer` to this one file, each entry point gated and bailing immediately) exists specifically to keep screen-reading inside "stuff already visible to you" (pick-phase portraits, your own screen at a moment you already lived through) and never extend it into live hidden-info territory. Tower/Roshan/barracks state stays post-match-only (OpenDota's parsed replay, Match Review's Objective timeline) by design, not by gap.
- **Why this one exception exists:** Valve's GSI genuinely never sends enemy/ally picks outside captain's own client (verified live, build 6975) — this is the only way to read something that's already visible on the player's own screen, same category as Dota overlay tools like [counterdraft](https://github.com/naghim/counterdraft) and [dota-counterpick-overlay](https://github.com/gestevao04/dota-counterpick-overlay) do.
- **Experimental: a "possibly forming" hint for an uncommitted pick** (`draftHoverHint` in `src/main/index.ts`, rendered in `draft.tsx` and the overlay's `DraftCard`). Draft Vision's existing pick-bar read already covers the whole top strip; this just stops discarding a hero it sees in your own team's slots that isn't a confirmed pick yet (GSI's own `pick.heroId` is still null before you lock, or an ally's slot updating before GSI's wave-merge catches up). No new capture region and no extra capture frequency — same read, used a little more. It deliberately never claims *whose* hover it is (could be your own tentative choice or a teammate's pick landing early) and is labelled "experimental, unconfirmed" in the UI: unlike the pick-bar reader's own calibrated crop positions, this hasn't been verified against a live game, so it's shipped the same way the rest of Draft Vision handles genuine position uncertainty — visible, labelled, and checkable, not silently assumed correct.
- **A real robustness bug, found and fixed: one failed capture used to erase an already-good confirmation chain.** `confirmDraftPicks` only accepts a slot once the same hero id is read in two reads back to back — a single transient capture miss (window briefly occluded, a capture race, a blank/corrupt thumbnail) used to null out `visionLastRead` in `receive()`'s vision handler, discarding whatever was already matching and forcing two more clean reads from scratch before anything could confirm again. A hero locked late in the pick window, right as the capture race or a window-focus hiccup happened to land, could end up never confirmed before pick/strategy phase ended. A real capture is now only ever compared against the previous *real* capture — a failed attempt just retries next tick with the chain intact. `matchSlot`'s own vertical-crop sampling also gained one more window (`[0.05, 0.95]`) alongside the existing three, since a different UI scale shifting the portrait vertically within the bar is a plausible real-world mismatch cause this adds coverage for without loosening the match-confidence gate (`best < 24 && runnerUp - best >= 5`) itself — that gate stays as strict as before; a genuinely ambiguous read still reports null rather than a guess.
- **Asked for, and declined: having Draft Vision keep reading the top HUD hero-portrait strip once the game goes live**, as a fallback for any slot pick-phase capture still couldn't confirm. The portraits themselves aren't hidden information — Dota shows all 10 at all times, win or lose vision — but "the pick-bar reader never runs once a game is live" is this project's own enforced boundary (`tests/guard.test.mjs` asserts it, not just documents it), drawn specifically so screen-reading never creeps from "bounded and gated" into "runs continuously during a live match," regardless of how harmless any one additional read looks in isolation. The fix above (not losing a good confirmation chain to one bad capture) is the real lever for "sometimes fails to recognize a hero in the pick phase" — it makes the *existing*, phase-bounded reader actually succeed more often, rather than widening what it's allowed to read.
- **Asked for again, specifically as a death-triggered capture — screen-reading the HUD at the moment you die to identify your killer — and declined again, for a second, independent reason this time: it can't be verified.** The idea itself is narrower than the live-HUD-fallback above (one-shot, reusing `captureDeathSnapshot`'s existing event gate, not continuous) and would read the kill-feed's own hero icons, not OCR — but this project already has a standing rule against shipping exactly this kind of unverified guess: `captureDeathSnapshot`'s own doc comment says analysis was never attempted on the death screenshot because "reliably reading arbitrary game state... from a small, noisy screen region isn't something this can verify works without a live game to test template-matching against, and shipping a guess there would be exactly the kind of made-up 'insight' this project avoids." The kill-feed's position, size, and how long it's still on screen by the time the death snapshot fires are all real unknowns with no live Dota session available to test against from this environment — building it now would mean guessing crop coordinates and shipping them unverified, the precise failure mode that rule exists to prevent. Built instead, and genuinely useful without that risk: **the same debuff-matching cross-reference knownThreat() already does for the inline lineup tip, now also applied to death-cause attribution.** `knownThreat()` takes an optional `beforeStatus` (the already-captured, zero-inference `deathCase.before.status` — your own stunned/silenced/disarmed/hexed/muted/broken flags right before you died) and checks it against each revealed enemy's own kit tags (`STATUS_TO_EFFECT` in `contextual-coach.ts`): if you died hexed and exactly one revealed enemy's kit can hex, that's real evidence pointing at them specifically, not a guess, and ranks above "has some dangerous ability" but below an actual confirmed kill. Surfaces as `recoveryAdvice`'s own evidence line — "Likely killer (matches the debuff you died under) · Name" — one real tier between "you confirmed it" and "just a lineup threat," built entirely from two things already being read for unrelated purposes, not a new capture.
- **Real limitation, not fixable:** the slot crop positions are fractions of window size calibrated for a typical 16:9 draft screen. A different aspect ratio or UI scale can throw them off — every portrait-matching draft tool in this space documents the same limitation. Settings → "Test draft vision" captures once and shows exactly what was read, for checking/retuning. `referenceFeatures` tries three Valve CDN paths per hero (`heroes/<slug>_sb.png`, `dota_react/heroes/<slug>.png`, `heroes/<slug>_lg.png`, same fallback order as the dashboard's own hero portraits) before giving up on that hero, so a very recently released hero missing from one CDN mirror still gets matched instead of being permanently unrecognizable — but a hero whose portrait genuinely can't be distinguished at the tiny crop size (two very similar-looking portraits) is a real limit of this approach, not a bug; "Test draft vision" shows exactly which slot it is.
- **Live map/building/player-position reading was asked for again and declined again**, now explicitly framed as "no vision hack, just game understanding." The framing doesn't change the mechanism: reading where things are on the map during a live match, even without calling it a hack, is reading state the game withholds from you until you have vision of it — there is no version of "simple game understanding" here that doesn't amount to that. What's buildable and already built is the death snapshot above (your own screen, a moment you already lived, never analyzed) — extending that to more checkpoints is on the table; reading live position or building state from the screen is not, regardless of phrasing.
- **Windows:** `desktopCapturer`'s window-thumbnail path can't see an exclusive Fullscreen DirectX window at all (it bypasses DWM) — when that happens, Draft Vision falls back to `desktopCapturer`'s full-screen (desktop duplication) source for the display Dota's window sits on, which does see it, and crops the same pick-bar strip since Dota fills the whole monitor in that mode. Borderless Windowed or Windowed mode still works through the normal window-thumbnail path and is still the more reliable option if the fallback ever mismatches a multi-monitor setup. The GSI feed and overlay need no OS permission on Windows.
- **Capture resolution is capped well below what `desktopCapturer` would otherwise request, on every platform.** Both the window-thumbnail path and the Windows-only full-screen fallback used to ask for a thumbnail sized to nearly the full window (up to 1600x1000) even though every portrait slot is matched down to a 16x16 feature (`THUMB` in `draft-vision.ts`) regardless — so the pick-phase poll (every 2.5s) and each death snapshot were paying real GPU readback/encode cost, and tripping the OS "recording this screen" indicator, for resolution nothing downstream used. `maxCaptureSize()` caps the request at 960x600 normally, tied into the same RAM-adaptive resource mode the overlay windows use (`resource-monitor.ts`): 640x400 once free RAM drops under 16GB. Same code path on macOS and Windows, so both get the reduction with no platform-specific change needed.
- **Enforced, not just promised:** `tests/guard.test.mjs` still bans every screen/memory/input/packet-capture API everywhere else in the tree, and specifically asserts this one file's two capture functions take `inPickPhase` first and bail out when it's false — the build fails if that gate is ever removed.
- **macOS:** the OS will prompt for Screen Recording permission the first time this feature actually captures. Same ad-hoc-signing risk already documented under "Puter AI coach" below: a grant is tied to the running binary's code signature, and this app's own auto-updater replaces that binary on every update, so a prior grant can silently stop applying after an update even though the Settings toggle still shows it on for the same app path — toggling it off/on (or removing and re-adding the app) re-establishes it. `screenAccessStatus()` in `src/main/index.ts` is informational only (used to pick the right error message after a real capture attempt fails), never a pre-check that blocks the attempt, precisely because this status can be stale in exactly that situation.
- **That design used to be documentation-only; the code contradicted it, found and fixed.** Both the draft-vision poll and `captureDeathSnapshotNow` were gating the actual capture attempt on `screenAccessStatus() === 'granted'` directly — exactly the stale-status trap the paragraph above warns about, so a real, working grant could leave both features silently doing nothing forever after an update, with no error and no recovery short of the manual reset steps. `canAttemptScreenCapture()` now gates only on `'not-determined'` (the one state where attempting would pop a surprise native permission dialog outside this app's own deliberate prompts) — every other status (denied, restricted, unknown, granted) just attempts the capture and lets the existing blank-frame/error handling take it from there, so a stale "denied" that's actually granted recovers on its own instead of needing a manual fix.

## Runtime "agents" (modules in the main process)
- **patch watcher** (`watchPatch`, every 10 min + startup): compares Dota `steam.inf` build to last seen. New build -> drop cached matchups, mark bundled seed stale, UI banner.
- **learner** (`learnProfile`): rebuilt from saved history/reviews on demand (idempotent, 120-day half-life). No separate training step; opening more matches = smarter.
- **draft engine** (`suggest`): seed + live + you + manual nudges, shrunk toward 50% on small samples.

## Data
- App data (downloaded hero/matchup data, local SQLite history, encrypted Puter/GSI tokens) lives in a hidden folder under the user's own Documents — `~/Documents/.dota-improviser` on macOS and Windows alike (`app.setPath('userData', ...)` in `src/main/index.ts`, set before anything touches `app.getPath('userData')`), not the OS default (Application Support / AppData\Roaming). Fixed by that path, not the app version, so an app update never re-triggers a download of data already on disk.
- `npm run data` = matchup seed + hero database + Valve kits + item-timing dataset. Written to `data/` for **dev use only** (`npm run dev`/`npm run build`'s browser-preview fallback reads these); the packager's `--ignore` excludes `data` from every `package:*` script, so a real install ships with none of it. No `npm run` command or file path is ever shown to the end user in the UI — empty-data states say what's happening (downloading, or press "Update data now") instead.
- First launch therefore has no hero/item/matchup data at all until it downloads: `app.whenReady()` checks for this (`!heroDb && !kitsDb && !timingsDb`) and calls `refreshData()` immediately, skipping the usual 60s debounce that exists only to avoid re-checking on every ordinary launch. The window shows and is usable instantly either way; `dataStatus` (Heroes page progress bar) reflects the download without blocking anything.
- Live coach scores GPM/XPM/last-hits against that hero's benchmark percentiles, tracks item achievements, and gives tips.
- Draft reveal: Dota sends picks in waves (or all at once in Turbo) via GSI `draft` when it chooses to; the app merges whatever arrives and keeps typed picks.

## Data sources (all free, public, allowlisted)
| Source | Used for |
|---|---|
| OpenDota `/heroes/{id}/matchups`, `/heroStats`, `/benchmarks`, `/heroes/{id}/itemPopularity` | counter pairs, rank/pro/turbo win rates, per-hero GPM/XPM/LH percentiles, item stages |
| OpenDota `/scenarios/itemTimings` | win rate by item purchase time -> coach achievement targets |
| OpenDota `/players/{id}` | Overview page's player scorecard: Steam avatar, persona name, rank badge only — never match history, that's still the separate `/players/{id}/matches` call above |
| Valve `dota2.com/datafeed/patchnoteslist` + `patchnotes` | which heroes changed in the latest patches -> older matchup data down-weighted, "patched" markers |
| Valve `dota2.com/datafeed/herodata` | stats, role levels, abilities (kits.json) -> mechanics model |
| `dotaconstants` (npm) | hero/item/patch catalogue |
| Local game files + Steam | build number (`steam.inf`), default item builds, signed-in account |
Windows Steam/Dota discovery (`src/main/local.ts: steamRoots`) checks the env-var and `C:\Program Files*` guesses plus every drive letter's conventional `Steam`/`SteamLibrary`/`Games\Steam` folder names — Steam installed to a non-system drive (common on a dedicated games SSD) was previously invisible, which also silently broke Steam-account detection and GSI config install since both derive from the same discovered root. `loginusers.vdf` gets one short retry: Steam briefly rewrites it around sign-in/account-switch, and a read landing mid-write shouldn't be treated as "no account" permanently.
Considered, not used: STRATZ GraphQL (needs a token and sits behind Cloudflare), Steam Web API match history (needs a key; OpenDota already covers it, and Valve gates match history behind the same "Expose Public Match Data" setting as OpenDota regardless of API key, so it adds nothing when that setting is off).
- **No download/export exists for a private player's own match history.** Checked: Steam's GCPD page (`steamcommunity.com/my/gcpd/570/`) is a rendered webpage, not a file, and the Steam Web API's match-history endpoints require that same Dota client setting to return anything at all — there is no self-auth bypass. The two real options with that setting off are (1) the GSI listener's own local capture (`saveOwnMatches`, below) or (2) hand-typing a manual CSV backfill (Settings -> "Matches without public sharing"); the app leads with (1).
- **A `saveOwnMatches`-captured match upgrades itself once OpenDota catches up.** `parseCompletedOwnMatch` (`src/main/gsi.ts`) stores the real Dota matchid, not a synthetic one, so `match:get` (`src/main/index.ts`) tries OpenDota first on every open and only falls back to the local single-player stub (no timeline, no team graph, no replay) when OpenDota genuinely has nothing yet. It used to check the local stub first and never look again, so a match that was later indexed/parsed by OpenDota stayed stuck showing "Local scoreboard" and blank charts forever.

## Game mechanics model (`src/shared/mechanics.ts`)
- **Computed (exact):** attribute scaling (STR 22 HP, AGI attack speed and 1/6 armor, INT 12 mana, universal 0.7 damage), armor reduction `0.06A/(1+0.06|A|)`, magic resistance, attack time, damage per second, and a Lanchester-style 1v1 duel (HP x DPS after armor).
- **Inferred:** every ability's effects (stun, silence, mute, root, hex, disarm, slow, fear, taunt, sleep, break...) from Valve's text; damage type and BKB-piercing from Valve's data fields. Data file `data/kits.json` (`npm run data`, or in-app update).
- **Learned:** a non-negative ridge regression over every hero pair in the seed finds how much each mechanic shifts win rates beyond overall hero strength. Where public data is silent a small game-knowledge floor applies. Prior strength comes from the data itself (empirical Bayes).
- **Used as the prior** for every matchup in the ranking: lots of real games override it, no games leave only the mechanics. Lineup analysis (damage mix, control counts, BKB-piercing, stealth) drives the "what to change" list with items.
- **The same lineup analysis also scores hero picks, not just items** (`poolFitPoints` in `src/shared/brain.ts`, reusing `teamProfile`/`rectify` from `mechanics.ts` rather than a second hand-tuned list): a candidate whose kit's damage type or control actually answers a gap `rectify` already found — too little magic damage on your side, too few hard disables, an enemy lineup that's physical-heavy — gets a real points bonus (`comp`, capped by `POOL_POINTS`), surfaced in the draft UI's existing `synergy` line. This is deliberately role-generic, not a hardcoded "mid checks both pools" rule: a support sees the carry's gaps the same way the carry sees the support's, since both are reading the same two `TeamProfile`s.
- Ranking = matchup edge (vs what overall strength predicts) + position fit (Valve role levels) + team composition + base strength + your comfort. A hero that is merely strong is not shown as a counter.
- **Neutral items** (`ItemInfo.neutralTier` in `src/shared/items.ts`, populated in `src/main/data.ts` straight from `dotaconstants`' own `tier` field — never a hand-maintained list) feed one real coach tip (`contextualCoach` in `contextual-coach.ts`): once a higher neutral tier is live than the one you're currently holding (own GSI item slots already include the neutral slot), it says so and names the tier you're behind on. The drop-time schedule itself (`NEUTRAL_TIER_MINUTES`, currently 7/17/27/37/60) is the same category of approximation as the Roshan/Aegis timer and the map timing alerts — Valve has moved these before, and this is the single place to update them. GSI carries no lane-equilibrium, creep-position or spectator data at all (same guardrail that blocks `buildings`), so that's the ceiling on how far "lane management" coaching can go from this feed; the static per-role laning text in `lanePlan` is what's left after that ceiling, not an oversight.
- **Percentile/score benchmarks auto-scope to the player's own real rank**, not the whole public pool. `bracketBenchmark` (`src/main/index.ts`) already called OpenDota's own `/benchmarks?hero_id&bracket&role` endpoint — verified live that `bracket`/`role` genuinely change the returned percentile curve, not silently ignored — but only when the player manually picked a bracket in Settings. `refreshOwnRank()` now fetches the player's own `rankTier` from their linked OpenDota profile once (on launch and on account link) and `activeCoachingBracket()` falls back to it automatically whenever the Settings dropdown is left on "Auto" — a Herald's 50th-percentile GPM is the real, lower number OpenDota reports for Herald players, not an invented fraction of the global figure. This also means the farm-pace tip's concrete "need N more by M:00" number (`coach.ts`) is automatically rank-scaled for free, since it already reads from the same scoped `bench` data.
- **Matchup item recommendations now name the specific threat instead of a generic "their disables"** (`counterItems` in `item-coaching.ts`, `NamedThreat` param): the same single most-dangerous enemy ability `knownThreat()` already identifies for the inline "Watch X's ability" tip — ranked by confirmed-killer first, then a real control effect, then matchup win rate — is now threaded into the Force Staff/BKB/Glimmer Cape reasons too, so a support facing Enigma reads "Reposition before Enigma's Black Hole lands" rather than a generic line. This is attribution, not a new mechanical claim: no hero-specific spell-interaction rules were added (a targeted-vs-AoE distinction like "does Lotus Orb block this" isn't something `Kit`'s ability tags can answer confidently, so no Lotus Orb/Linken's Sphere branch was added either — that would be guessing). The early-game Magic Stick reason also now mentions bypassing evasion by name when the opposing lineup has an evasion hero (PA, Brewmaster, or any kit tagged `evasion`), since that's a real, zero-inference Dota mechanic (spells ignore evasion), not a new claim.
- **Item recommendations now carry a small self-learning nudge from the player's own match history** (`ItemBias`, `itemBiasFor()` in `src/main/index.ts`): reuses `learnItems()` — already built for the Heroes page build planner — to read this player's own win-rate-with vs win-rate-without delta for each item on this hero (3+ games each side before it counts), and feeds it into `counterItems()`'s scoring as a ±10-point nudge. This is the actual "proved useful or not, from your own games" signal the item list should reflect, with zero fabricated data and no second learning system — just the existing one reused for a new consumer. Memoized per account+hero (`itemBiasMemo`) since `learnItems` scans every saved review and `refreshCoachView` runs roughly once a second; recomputing it every tick would be pure waste.
- **A second, AI-assisted mode for mid-game item analysis** (`ITEM_ANALYSIS_QUESTION`, `askLiveCoach` reused — see "Puter AI coach" below for the on-demand button and the rate-limited automatic check-in).
- **Off-role laning advice** (`laningGuidance` in `contextual-coach.ts`): the generic per-role `lanePlan` text above assumes the hero is a typical pick for that role. When it isn't — a core hero (Valve's own `hero.roles` tag has `Carry` but not `Support`) put in a support slot, like Sniper hard-supporting, or the reverse, a support-tagged hero pushed into a core slot — the advice would otherwise quietly assume a job the hero doesn't have. `laningGuidance` checks `hero.roles` against the selected role and swaps in advice that names the mismatch explicitly (farm priority for an off-role support-as-core, poke/wards-over-last-hits for an off-role core-as-support, using `hero.ranged`), surfaced as a `warn`-level tip instead of the usual `info` one so it stands out. `CoachingContext.offRole` also threads into the Puter prompt (`buildPuterPrompt`'s live `compact.offRole`) so free-form AI answers in the overlay account for it too instead of assuming the hero's usual job.
- **Percentile-based coaching (score, GPM/XPM/LH percentile bars, "low pace" warnings) only runs for matchmaking games** (`frame.matchmaking` gate added to `pct()` in `src/shared/coach.ts`). A practice lobby or Hero Demo can run bots, cheats or sandbox gold/XP rates — comparing that against the real public benchmark ladder produced a technically-correct but meaningless result (e.g. a genuine Hero Demo session reporting "GPM 4,847 · 99th percentile"). `frame.matchmaking` already distinguishes this (it's how the overlay's own header already labels a session "Practice" vs the real mode), and this is the first place that label's distinction was actually enforced on the numbers, not just the display text; raw GPM/XPM/last-hits still show either way, only the percentile/score/low-pace judgments are suppressed outside matchmaking. This never touches `sessionGameType` (the player's own manual Ranked/Normal/Turbo/Ability-Draft choice in session setup) — detection and selection are, and stay, two separate things.
- **Richer live status, straight from GSI** (`Frame.status`/`buybackCost`/`buybackCooldown` in `model.ts`, populated in `gsi.ts`'s `projectFrame`): Valve's own `hero` GSI block already reports your hero's current stunned/silenced/disarmed/hexed/muted/broken/magic-immune/smoked booleans and your `player` block reports buyback cost and cooldown — all zero-inference, exactly what the client already knows about your own hero. Shown as a compact status-chip row in the overlay (`StatusStrip` in `ui.tsx`) above the usual stats, nothing new read from the game, just more of what was already in the feed and previously discarded.
- **Death breakdown: a factual "what happened" line, from the same already-read fields above.** The dead frame GSI sends right after a death has its status flags already cleared, so `deathBreakdown()` (`live-coach.ts`) reads them from the *previous*, still-alive frame instead — captured once as `deathCase.before` the moment `alive` flips to `false` (`src/main/index.ts`) and threaded into `recoveryAdvice()`. Reports health/mana percent and which debuffs (stunned/silenced/disarmed/hexed/muted/broken — not magic-immune, that's not a debuff) were active right before dying, plus buyback availability, e.g. "Died at 8% HP while silenced, disarmed · Buyback ready for 1,850g". Zero new capture and zero guessing: this never attempts to name a killer (that's still `deathCase.killer`, the player's own manual confirmation, or the separate lineup-threat match) — it only surfaces the player's own state at the moment of death, which the feed already had and was previously just thrown away.
- **Further GSI fields added, same "own-player, zero-inference" category:**
  - **`abilities` GSI section** (added to `allowedGsiSections` — same category as `items`/`hero`, your own spell levels/cooldowns, nothing about anyone else) feeds `Frame.abilities` (`ownAbilities` in `gsi.ts`). Surfaces as an "Ult ready" chip in `StatusStrip` and a live tip in `coach.ts` the moment your ultimate comes off cooldown.
  - **HP%/mana%** (`hero.health_percent`/`mana_percent`) → `Frame.healthPct`/`manaPct`, shown as two slim bars in `StatusStrip`, plus a real "retreat now" warning in `coach.ts` under 25% health (or hold key spells under 15% mana).
  - **Reliable vs. unreliable gold** (`player.gold_reliable`/`gold_unreliable` — only unreliable gold is lost on death) sharpens the existing "unspent gold" tip to say how much is actually at risk, instead of a flat total.
  - **Per-item cooldown/charges** (`ownItemState` in `gsi.ts`, same inventory block `ownItems` already reads — just the fields that function discarded) shown as `ItemCooldowns` in `ui.tsx`: only the items actually on cooldown right now, nothing shown when nothing is.
  - **Talent picks** (`hero.talent_1..talent_8`) → `Frame.talents`, shown as `TalentTiers` tier pips (10/15/20/25, left/right). GSI gives no talent *name*, only which side was picked — so that's all this shows; no talent text is guessed or invented.

## Game dynamics (own game feed only)
- First blood (which team, you or not), double/triple/ultra kill and rampage (kills chained within 18 s), kill streaks, and a kill-lead momentum graph come from your own kill count, kill streak and the public team score.
- Tower, Roshan and barracks state are **not** in a player's feed (spectator-only `buildings` is blocked by the guardrails). They appear post-match in Match Review's Objective timeline, from OpenDota's parsed replay, with Dota's own gold/XP advantage graph. This means **Live & Coach's win estimate** (`matchEstimate` in `src/shared/match-outlook.ts`) can only ever move on team kills, the revealed lineup, your own pace, and your own KDA — a tower or Roshan lead, enemy net worth, or anyone else's KDA only registers if it also shows up in kills or GPM/XPM, and a split-push lead genuinely can't, since the game state it'd need is exactly what the guardrail blocks. The Match outlook card says this explicitly rather than showing a number that looks wrong with no explanation. The factor list: lineup draft-win prior (decaying as the match goes on), live team-kill lead (scaled by game length and total kills), team scaling/balance once both full lineups are known, your GPM/XPM pace vs. the hero's own benchmark, respawn downtime, and your own KDA ratio ((kills+assists)/(deaths+1)) — each bounded small and summed through a logistic, same shape as before, just with the extra own-data factor and nothing fabricated for data GSI doesn't carry.
  - **Rebalanced to a requested 30% kills / 40% everything-else split, with the 30% that was meant for towers dropped rather than silently kept on the old 2-factor balance.** Towers/Roshan/barracks genuinely cannot be a live factor — `allowedGsiSections` in `guard.ts` excludes `buildings` outright, enforced by `tests/guard.test.mjs` — so there's no live substitute for that third of the requested weighting; it stays where it's actually available, OpenDota's real parsed tower data in Match Review (`ObjectiveTimeline`/`TeamOverview`). What's rescaled is the ratio between the remaining two: `KILL_WEIGHT`/`OTHER_WEIGHT` in `matchEstimate()` renormalize the kill-lead term and the "everything else" bundle (draft prior, scaling/balance, pace, respawn, KDA) to the requested 30:40 ratio of their combined budget (kills get 30/70, everything else gets 40/70) — the cleanest a percentage split translates onto a logistic blend of unlike units, and no more exact than that, same caveat as every other approximated constant in this file. The dashboard's own outlook card (`live.tsx`) already explains the tower/Roshan gap in plain text next to the number, unchanged by this.

A rune/day-night/stack/pull crossing landing in any of the skipped ticks in between was never checked against at all, not delayed — it just never fired, which is why water/power/bounty runes and the support pull heads-up could all silently go missing. Fixed with a dedicated `mapTimerClock` (`src/main/index.ts`) that tracks exactly how far `dueMapTimers` has already checked, updated on every frame tick regardless of whether `refreshCoach` also fired that tick, so the checked window is contiguous.

## Overlay sizing and layout
- **Hard ceiling: the overlay never exceeds half the monitor in either dimension** (`overlayBounds` in `src/main/overlay-layout.ts`), regardless of size setting, editing/setup expansion, or view — a companion HUD should never visually compete with Dota's own screen. Every other width/height target in that function is a smaller *preference* under this cap, never a way around it.
- **The expanded/large card's win-estimate is a one-line gauge, not a chart** (`WinTick` in `src/renderer/match-outlook.tsx`): a marker on a 0–100 track against the 50% baseline. The full scrubbable `OutlookGraph` (gridlines, axis, drag-to-explore) still exists and is still used on the dashboard's own Live & Coach and Overview pages, where there's room for it — only the in-overlay `OutlookCard` was swapped, since a chart was the single biggest vertical cost in a space-constrained HUD for a number that only needs to say "ahead or behind, by how much."
- **Compact card items show as an icon + ETA chip, not prose** (`ItemRecommendation.etaMinutes`, `MatchItems`'s `compact` branch in `src/renderer/ui.tsx`): the full reason/timing/goal sentences only render in the large card now capped to one item instead of two, since a second full prose card was pure vertical weight the compact chip row already replaces with no text at all.
- **`.overlay-view`'s padding used to be split across four separate, partially-overriding CSS rules** left behind by earlier style passes (the file's own "v3/v4 layer" sections each patched the previous one), so the actual edge padding depended on cascade order rather than being stated once — consolidated into a single rule in `src/renderer/styles.css`.
- **The death-snapshot card's header text was getting clipped — a real CSS gap, found and fixed.** `.death-snapshot-card` was capped at `max-width: 280px`, the one outlier among this family of cards (every other one — `.card`, `.lane-card`, `.draft-card`, `.coach-card` — caps at 380px), while `.card-head` has no wrap (`flex-wrap` was never set) and both its "What you saw" tag and "Closes on its own" sub-label assume enough width to sit on one line; squeezed into 280px minus padding, the row ran out of room and visibly cut off mid-word instead of wrapping. Brought to the family's shared 380px and gave `.card-head` `flex-wrap: wrap` (with `min-width: 0` on the tag and `white-space: nowrap` on the sub-pill so it still reads as one chip when it does wrap) so this degrades gracefully on any card, not just this one. Also brought its translucency in line with the rule below (.96 opaque → .86 + blur) — it had been added after that pass and was never updated to match.
  - **Still clipping sometimes, for a second, different reason: the screenshot itself had no height cap.** `.death-snapshot-card img` rendered at `width: 100%` with no `max-height`, so the full resized screenshot (up to 720px wide, ~405px tall at 16:9) stacked below the main coach card — itself tall in detailed mode — could push combined overlay content past the hard half-monitor cap (`overlayBounds`), which the root `.overlay-scroll:not(.interactive)` falls back to `overflow: hidden` for if that cap ever binds. On a smaller/laptop monitor that clipped text mid-card, the same symptom as the header-wrap bug above but a different cause. The image is now capped at `max-height: 150px` (`object-fit: cover`) — still plenty to recognize what was on screen for a quick self-review glance, which is this card's only job, and meaningfully lowers how often the shared half-monitor cap gets hit in the first place.
- **A visible size-pop on every overlay appearance, found and fixed.** `makeOverlay()`'s `BrowserWindow` is created at a placeholder 360x186 and only resized once the renderer's `ResizeObserver` reports its real content height over `overlay:height` — but `requestOverlay()` used to call `window.showInactive()` immediately on creation, before that first real measurement ever arrived, so the overlay visibly popped up at the placeholder size and then jumped to its real size a tick later, every single time it appeared. `presentOverlay()` now defers that first show (`overlayPendingFirstShow`) until the `overlay:height` handler has placed the window at its real, measured size — every later show (the window re-appearing after `trackOverlay()` hid it during an alt-tab, say) is unaffected, since `overlayHeight` is already known by then. The achievement/map-timer/tip height handlers also gained the same "skip if unchanged" guard the main overlay's already had, for the same reason that one exists: avoid redundant `setBounds` work on every identical measurement.
- **Every overlay card is translucent, not a solid panel.** The coach/lane/draft cards and every toast (achievement, map-timer, tip, recovery) used to fill at .9–.96 alpha — on top of a game, that reads as an opaque box rather than an overlay. All of them now fill around .76–.8 with `backdrop-filter: blur(6px)` added to keep text legible at the lower opacity, so the game underneath still shows through. This is purely a fill-opacity change on the card's own CSS, not the `BrowserWindow`'s `transparent: true`/`opacity` setting — those windows were already transparent outside their rendered content; the cards drawn inside them were the part that looked solid.

## Puter AI coach
- An optional AI Q&A layer (`@heyputer/puter.js`), signed in from Settings, token stored via `safeStorage` (OS keychain), never sent anywhere but `api.puter.com`/`puter.com` (both allowlisted).
- **Pinned to an exact version (`2.6.3`, no `^`), deliberately — checked and confirmed why during a dependency-update pass.** `npm audit` flags every `@heyputer/puter.js` release from `2.6.4` onward as depending on a vulnerable `postal-mime` (high severity, quadratic-CPU header-decoding DoS). A caret range would silently pull that version range back in on the next `npm install`/`npm update`, so this one stays an exact pin rather than `^2.6.3` until upstream ships a release that doesn't carry it — re-check `npm audit` before ever loosening this one.
- The prompt (`buildPuterPrompt` in `src/main/index.ts`) is grounded in the app's own real data, not left to the model to guess: the selected hero's actual ability tags from `kits.json` (ultimate/passive, damage type, BKB-piercing, status effects), recent Valve patch notes that touched that hero, your computed matchup edge vs the known enemies (same pair data the draft ranking uses), and the top 3 matching entries from the built-in glossary (`src/shared/knowledge.ts`) — a local lookup, no extra network call. Where the app has no data for something, the prompt tells the model to say so rather than invent a number.
- Capped at 220 output tokens per Know-page answer (112 live) — the prompt itself also tells the model to lead with the concrete recommendation in at most 3 short sentences instead of a wall of caveats; the Know page's own on-page knowledge search works at `src/shared/corpus.ts` (hero kits + items + recent patch notes + glossary, ~700 docs, memoized in `getCorpus()`) and works without calling the AI at all.
- The prompt tells the model to answer in plain prose (no markdown headings/bold/bullets, no emoji) so it reads naturally in-app; `stripMarkdown()` in `src/main/index.ts` also cleans the response defensively in case the model ignores that.
- **A canned, threat-aware "analyze this fight" question, reused everywhere instead of duplicated per caller** (`ITEM_ANALYSIS_QUESTION` in `src/main/index.ts`): asks for a prioritized item call naming the biggest confirmed threat and current items, and only to mention team-wide itemization if the lineup actually calls for it — grounded by the same `buildPuterPrompt` live context (hero, items, enemies, allies, `coaching.items`/`tips`) every other live question already gets, so the model has the real situation instead of having to guess at it. Two surfaces share it: the existing "Ask Puter about this fight" button (now on both the dashboard's Live & Coach page and, newly, the overlay's own detailed card — `onAnalyzeItems`/`itemAi` in `CoachCard`, wired through a new `window.overlayApi.analyzeItems()` → `overlay:analyze-items` IPC channel) and the automatic check-in below. This is deliberately the second, AI-assisted mode next to `counterItems()`'s rule-based knowledge-base list above — not a toggle replacing it, since the rule-based list has zero latency/quota cost and the AI mode adds judgment on top of it rather than instead of it.
- **An automatic, rate-limited version of the same question** (`autoItemAnalysis` feature, off by default — Settings, "Intelligence" group; `maybeAutoAnalyze()` in `src/main/index.ts`, called at the end of every `refreshCoachView()`): fires the same `ITEM_ANALYSIS_QUESTION` itself, at most once per real 4-minute window (`AUTO_ANALYSIS_COOLDOWN_MS`), and only when the game phase or the top rule-based item recommendation has actually changed since the last auto-fire (`lastAutoAnalysisKey`) — so a held-steady situation doesn't needlessly re-ask on every tick, and it reacts to a new threat or phase instead of re-confirming the same one. The answer surfaces through the existing tip-toast pipeline (`emitTip('AI: ' + answer, ..., 'ai-analysis')`), the same fading reminder strip coaching tips already use, rather than a new always-on card. Off by default and requires the overlay assistant feature too, since this spends the player's own Puter quota without an explicit click — errors (not signed in, a previous answer still loading) are swallowed silently here, unlike the explicit button, since this is a background convenience the player never directly asked for in that moment.
- **Dota shorthand, resolved silently:** the prompt spells out common hero nicknames (PA, PL, SF, QoP, CM...) and item slang (BKB, MKB, Aghs, Hex...) and tells the model to resolve them itself rather than asking the player to clarify — it's a general-knowledge LLM, so this is instruction, not a lookup table the app maintains. It's also told to answer confidently from general Dota knowledge when the app has no matching data for this hero/matchup, and only mention "no data" when that gap actually changes the advice (e.g. no real win rate to cite) — the model used to hedge about missing app context even for plain counter-pick questions it already knew the answer to.
- **Keychain/DPAPI persistence — verified, with a real limitation found and fixed.** `safeStorage` backs onto the OS keychain on macOS and DPAPI on Windows automatically (Electron's own abstraction, no platform-specific code needed; not independently tested on Windows from this Mac). On macOS specifically: `safeStorage.decryptString` is **synchronous**, and a keychain item's ACL can be scoped to the signing identity that created it. Built two throwaway apps with different ad-hoc signatures (`codesign --sign -`, same as this app's own packaging) and confirmed decrypting one's blob under the other **hangs with no catchable error**, not a clean rejection — a real risk for an ad-hoc-signed app across rebuilds, since a synchronous hang in the main process stalls everything (GSI, broadcasts, all IPC), not just that one call. Fixed: `getPuterClient(attemptDecrypt)` only touches the stored token on a deliberate user action (sign-in, ask, sign-out); the eager startup check (`puterStatus()`, called from `index.tsx` on mount) never attempts the decrypt, so a stale token from an older build can no longer freeze the app on launch — verified by seeding a fake stored token and confirming the app replies in milliseconds instead of hanging. A real distribution Developer ID signature (stable identity across rebuilds) would remove the underlying risk entirely; ad-hoc signing (the only option without a paid Apple cert) cannot.

## Self-learning and self-updating
- **Patch-aware profile:** your history/reviews are re-weighted on every run: recency half-life 120 days, and each patch older than the current one keeps 65% of its weight.
  - **A real gap, found and fixed: a locally-captured match (`saveOwnMatches`) never carried a patch at all, so it never aged by patch.** `parseCompletedOwnMatch` in `gsi.ts` always stamped `patch: ''`, because GSI itself reports no patch/version field for a completed match — there's no official mapping from the local Steam build number to a human patch name ("7.42") shipped anywhere this app can read. `learnProfile`'s patch-age decay (`behind()` in `brain.ts`) can't place an empty string on the patch timeline, so it silently fell back to zero patch-decay for every local match, leaving only the 120-day recency half-life to age it — an old local-only match kept full patch-relevance weight forever, which is exactly the "old patch's info colliding with the new Dota version" failure this decay exists to prevent. `parseCompletedOwnMatch` now takes a `currentPatch` argument, and its one real caller (`receive()` in `index.ts`) passes `catalog.patch` — the app's own already-tracked latest known patch, itself refreshed by `watchPatch()` on every Dota update. Not a guess: it's the truest honest value available for "what patch was live when this match was actually played."
  - **Asked for: a heavier learning/ML library for the self-learning side.** Considered and declined, same reasoning this file already documents for the vector-DB question above: every learning mechanism here (ridge regression for mechanics, a small logistic fit for comfort-vs-counter weighting, a brute-force k-NN over saved matches) is sized to what it actually has to work with — one player's match history, in the dozens to low hundreds, not a training set a real ML library earns its keep on. Swapping in a heavier dependency here would add install size, attack surface and a black box in place of code this project can actually explain in its own tips, for no real accuracy gain at this data scale. The two real, concrete learning gaps found this pass — the missing patch stamp above, and death-cause attribution below — got fixed directly in the existing mechanisms instead.
- **Fitted weights:** a small logistic regression on your saved matches decides how much hero comfort counts vs counter edge (needs 25+ matches; bounded; defaults until then).
- **Personal baselines:** the live coach also compares you to your own average GPM/XPM/LH on the hero.
- **Auto data refresh:** a new Dota build (steam.inf) or data older than 14 days triggers a background refetch into the user data folder, which overrides the bundled seed/hero data. `Heroes -> Update data now` used to force the full ~500-request OpenDota refetch unconditionally on every click, even seconds after a real refresh finished; it now runs the same `dataNeedsRefresh()` check (patch changed, a dataset missing, or the last refresh older than 14 days) as the background scheduler, and just says "Hero data is already up to date" instead of starting a download it doesn't need.
  - **A real gap, found and fixed: hero/item/ability data could get stuck a full patch behind, on both platforms, with the UI insisting it was up to date.** `dataNeedsRefresh()`'s `patchChanged` flag only flips from `watchPatch()` comparing Dota's own `steam.inf` build number against the last one seen — that's local-install detection (depends on finding the right Steam folder; see the Windows multi-drive note under "Data sources" above), not a check against the app's own bundled `dotaconstants` catalog. When that build-number watcher never ran (an update shipped a newer `dotaconstants`, or local discovery simply missed a bump), nothing else ever re-checked, so `heroDb`/`seed` stayed stamped with whatever patch they were last built against indefinitely — "Hero data is already up to date" even while `catalog.patch` (read straight from the installed `dotaconstants` package, OS-independent) had already moved on, and the Mechanics guide, item tiers and ability text all read stale right along with it. `dataNeedsRefresh()` now also compares `heroDb.patch` (the patch `buildData` actually stamped the cached hero/item/kit data with) against `catalog.patch` directly — no Steam/local dependency, so it can't go blind on Windows (or anywhere else) the way the build-number watcher can.
  - **A second, related bug: abilities with a genuinely zero cooldown/mana cost read as a broken display, not a fact.** Valve's own `herodata` feed reports a flat `0` for some abilities (Clinkz's Searing Arrows, Death Pact and Infernal Shred all come back `cooldowns: [0]` straight from `dota2.com/datafeed/herodata` — verified live, not a guess) — real data, not a missing field, but the Mechanics guide rendered it as "Cooldown 0/0/0/0", indistinguishable from a parsing bug. `nums()` in `src/main/guide.ts` now collapses an all-zero cooldown/mana list to `''`, so the UI omits the line entirely — the same treatment it already gives a field Valve sends nothing for — while a real value (including a genuine `0` mixed with nonzero levels) still renders in full.
- **Progress total was unstable mid-refresh** (`buildData` in `updater.ts`): the item-timing phase's slot count (up to 4 per hero) wasn't known until the main per-hero loop finished, and used to be added to the already-reporting `total` at that point — so the progress bar's own denominator could jump from ~509 to 800+ partway through a refresh. Reserved as a fixed upper bound from the start instead of growing dynamically, so the denominator is one stable number for the whole run.
- **Situational k-NN lookup, not a vector database:** `similarMatchupRecord` in `src/shared/brain.ts` finds your own past matches whose enemy lineup overlaps (Jaccard similarity, ≥2 shared heroes, ≥3 qualifying matches to report anything) with the one you're facing now, and reports your real record against them — "vs these lineups, you won 2/3" on the Draft page. This is deliberately a brute-force k-NN over your own already-stored match reviews, not a vector database: a real vector DB (ANN index, embeddings service) is built for searching millions of high-dimensional vectors fast, and a single player's saved-match count is in the dozens to low hundreds — comparing against every one of them directly takes microseconds, so an ANN index would add infrastructure and a dependency to solve a problem that doesn't exist at this scale. It complements rather than replaces `fitWeights`' global logistic fit: that fit captures one scalar "counter edge vs comfort" trade-off across all your matches, which structurally can't see "you specifically do well against lineups shaped like this one" — only a direct lookup over real past lineups can (the same limitation a 2013 Stanford CS229 Dota 2 recommender paper found with logistic regression over hero features, which is why it also moved to a distance-weighted kNN).
- **Your own build pattern, not the guide's:** `personalBuildPattern` in `src/shared/brain.ts` reads what you actually bought across your own saved match reviews for a hero (purchase events already captured for Match Review's timeline) and reports it on the Draft & Builds page's build planner, next to — not instead of — OpenDota's community item-popularity data and Valve's own default build. Needs 3+ of your own games with purchase data on that hero before it reports anything (same comfort threshold as `fitWeights`), and shows a win rate for an item only once it's been bought in 3+ of those games, so one lucky or unlucky game doesn't look like a trend. This is for your own individual refinement: seeing where your real habits diverge from either guide, not a recommendation engine of its own.
- **Screen captures are never persisted.** Draft Vision's pick-bar reads and the death snapshot only ever live in memory for the current session (module-level variables, broadcast straight to the UI) — never written through `store.set` (the SQLite-backed persistence every other setting/history uses). `tests/guard.test.mjs` asserts this directly by scanning for any `store.set`/`store.get` call that touches those values. The one deliberate exception is `rememberPortrait`'s labelled-portrait samples (you explicitly label a slot to teach it a cosmetic/skin variant) — that's opt-in per-label training data, not an automatic capture, and is already capped to the last 60 labels.

## Performance
- React/icons are split into their own `vendor-*` chunks (`vite.config.ts` `manualChunks`) so an app update's own code can be refetched without re-downloading libraries that didn't change; this dropped the main bundle below Vite's 500 kB chunk-size warning.
- The renderer never computes anything expensive twice: `getCorpus()`, hero detail, draft rankings and the matchup/profile models are all memoized against their real inputs and only rebuilt when a dependency actually changes.
- **Windows overlay z-order.** The overlay and achievement windows run at Electron's `'screen-saver'` always-on-top level (the highest cross-platform level it exposes — bumped up from `'floating'`, which some games and other always-on-top tools, Discord's overlay included, could still draw over by re-asserting their own z-order afterward). On Windows only, `reassertOverlayZOrder()` (`src/main/index.ts`) calls `moveTop()` on both windows roughly every 1.6s while the foreground-window tracker confirms Dota is actually focused — a native window-management call on this app's own windows, not a hook into Dota, and deliberately independent of the "Follow Dota" monitor-tracking setting since it's a different concern (z-order, not placement) that should run however the player has the overlay positioned. This covers Borderless Windowed and Windowed Dota; exclusive Fullscreen still bypasses the Windows desktop compositor (DXGI) entirely, so no window level or z-order call can reach it there — Companion mode or Borderless Windowed remains the real answer for that case, same as documented above.
- Backgrounded correctly instead of "optimized" with invented knobs: Electron's `backgroundThrottling: true` lets the OS throttle windows that aren't visible; the patch watcher runs every 10 minutes and the self-update check every 6 hours, not on a tight loop; the overlay is a small (360x186) non-shadowed panel, not a full-screen transparent surface. There's no lever here called "GPU utilization" or "garbage collection" to add — V8 already manages memory, and Electron's own throttling already covers idle windows; inventing toggles for these would be decoration, not optimization.
- **"Keep running in the background" (`backgroundTray` feature, on by default):** closing the dashboard window hides it and keeps a tray icon (Windows system tray / macOS menu bar) instead of quitting, so GSI, the overlay and live coaching keep working — "Quit" on the tray icon is the real exit. Hidden, the dashboard is fully backgrounded by Chromium's own throttling (above); nothing new is spent keeping it around. On macOS the Dock icon hides too while backgrounded, matching "lives in the menu bar" apps; it returns when you reopen from the tray. Disabling the feature in Settings restores "closing the window quits the app."
- **Idle windows are actually freed, not just hidden.** The achievement and map-alert pop-up windows are each a separate Chromium renderer process; `hideOverlay()` used to only `.hide()` them, so once created they stayed resident (and kept consuming RAM) for the rest of the app's run even during a long dashboard-only session between games. `scheduleAuxWindowIdleClose()` (`src/main/index.ts`) now actually `.close()`s whichever of the two is still hidden after an idle delay with no overlay activity (below), cancelled immediately by `requestOverlay()` the moment the overlay is shown again — both windows are cheap to recreate (just `BrowserWindow` + `loadFile` with a hash, no state to rebuild), so there's no responsiveness cost to freeing them when idle. `before-quit` also clears every timer the session can have running (`moveTopTimer`, `toastTimer`, `matchSummaryTimer`, `auxWindowIdleTimer`, the resource monitor below), which a few had been missing from that list.
- **Resource usage scales with how much RAM the machine actually has free** (`src/main/resource-monitor.ts`, `pickResourceMode()`): every 30s (started at 5s — that was itself the overhead this module exists to cut, a mode flip doesn't need to react that fast) it checks `os.freemem()` against a fixed 16GB line and sets `LiveState.resourceMode` to `'full'` or `'minimal'` — nothing to configure, it just adapts. Draft Vision's own capture resolution reads this same mode too; see "Draft vision" above. There isn't a continuous graphics cost the app itself controls (Chromium owns compositing), so the only honest levers under "use fewer resources" are the ones that actually move: in `'minimal'` mode, idle achievement/map-alert/tip windows close after 60s instead of 5 minutes (freeing their renderer processes sooner), the tip-reminder row caps at 2 simultaneous chips instead of 3, and the Windows z-order reassertion interval relaxes from 1.6s to 3s. This is in addition to, not instead of, the inherent tradeoff documented below: every extra always-on-top alert window (achievement, map-timer, tip) adds some real compositor cost while visible, which is why `features.toasts` already gates all three at once for anyone who wants to turn the cost off entirely rather than just scale it down.
- **Cursor hover-fade now covers every toast window, not just the main card.** `updateHoverFade` (`src/main/index.ts`) faded the main overlay card to near-transparent while the cursor sat over it, so it never blocks the view — but the achievement/map-timer/tip windows were left out entirely, so hovering one of them never faded it the way the main card already did. The same 150ms poll now checks the cursor against all four windows (`hoverFadeState`, a `WeakMap` so a destroyed/recreated window's old entry is dropped automatically) and fades whichever one the cursor is actually over; each toast window's opacity resets to 1 whenever it's freshly shown, so a stale faded value from a prior hover can't carry over into its next appearance. Toasts were also shrunk (padding/icon/type) — the full size read as distracting for what's meant to be a brief reminder.
- **A rolling resource log, exportable from Settings** (`resource-monitor.ts`'s in-memory ring buffer, 1 hour of 5s samples — RSS, free/total RAM, process CPU%, and how many overlay windows were up — never written to disk until exported, same "never persisted automatically" rule as draft vision). Live & Coach's "Resource usage" panel shows the current mode in plain language and a button that writes the buffer to a JSON file (`resource:export` IPC, same `dialog.showSaveDialog` pattern as the existing redacted-GSI diagnostics export next to it) — meant for actually diagnosing a reported slowdown (which window types were up, how RSS moved) rather than live-rendered chart, since rendering one more thing live is exactly the kind of overhead this feature exists to avoid adding.

## Flow
1. First run: detect Dota install + Steam user -> offer "Use my Steam account" -> history loads.
2. Install GSI cfg (one click into `game/dota/cfg/gamestate_integration`), add `-gamestateintegration` launch option.
3. Draft: type enemy picks (dashboard, or overlay hotkey Ctrl/⌘+Shift+O, which opens draft editing before a hero is live and the AI assistant once one is). Suggestions appear instantly from seed, upgrade when live data lands.
4. In game: live coach/lane card (any practice, normal or ranked game — GSI own-player data only, never reads opponents or hidden info). Ctrl/⌘+Shift+H hides; Ctrl/⌘+Shift+C toggles Compact/Large.
5. After game: open match -> review -> profile relearns.
6. After a Dota patch: watcher flags it; `npm run seed` refreshes the offline table; nudges halve until you re-confirm.

## Updating
- Game patches: automatic detection (above). Optional: re-run `npm run seed`.
- App updates: the repo is public, so `ReleaseUpdates` (`src/main/release-updates.ts`) polls its releases every 6h plus shortly after launch with no token needed, and downloads + sha256-verifies a matching installer automatically once one exists, all in the background. Every GitHub API request sets a `User-Agent` header — GitHub's API returns a bare HTTP 403 (not a rate-limit message) to any request missing one, and Node/Electron's `fetch` sends none by default; this broke update checks on every OS, not just the one it was first seen on. A GitHub token (Settings) is optional, only useful past GitHub's unauthenticated rate limit (60 requests/hour). With the "Launch verified updates automatically" feature on, it then launches that verified installer itself as soon as you're not mid-game, instead of waiting for a click in Settings. It still can't make that launch invisible: this app's own fair-play guardrail (`tests/guard.test.mjs`) blanket-forbids spawning other processes anywhere in the source tree, and macOS separately requires your password for anything outside your own account — both are deliberate, not gaps to route around.
- **Windows installer and macOS packaging now cover only Apple Silicon** (`package:mac-intel` and the `macos-x64` build leg were removed) — ship what's actually tested and signed, not an Intel build nobody verifies. The Windows installer (`scripts/windows-installer.nsi`) carries full VERSIONINFO (product name, file/product version, publisher), an app icon, a real uninstaller with Add/Remove Programs registry entries, and the packaged `.exe` itself carries matching `win32metadata` (FileDescription/ProductName/LegalCopyright) via `@electron/packager` — an unsigned EXE with no version info and no uninstaller is exactly the shape Windows SmartScreen and antivirus heuristics treat as most suspicious, so this closes real gaps in that heuristic profile.
- **What Windows trust actually requires, and what this can't fake:** SmartScreen reputation and Defender heuristics are earned by download volume and, above all, a paid code-signing certificate (EV or OV Authenticode) — there's no client-side setting or build flag that substitutes for that, and nothing in this app tries to evade or spoof either system (that would itself look exactly like malware behavior and get flagged harder). The real levers taken here are legitimate: no process spawning (already enforced by `tests/guard.test.mjs`), no packer/obfuscation, `RequestExecutionLevel user` (no unnecessary admin elevation, itself a reputation signal), restrictive Electron fuses, and complete version metadata. Getting an Authenticode certificate and signing both installers is the one remaining step that would actually remove SmartScreen's "unrecognized publisher" warning — out of scope for this change, left to the project owner.
- **Release tag convention:** a real, user-facing release is tagged with the bare version (`1.0.1`, not `v1.0.1`), published (not draft) and not marked prerelease — that's what `selectRelease()` in `release-selection.ts` will offer the auto-updater, and it explicitly rejects anything draft or prerelease regardless of its tag (tested in `tests/release-and-history.test.mjs`). Tags prefixed `v` or `f` (`v1.0.2-rc1`, `f1.0.2-ci17`) are testing/CI-only — keep them as drafts (or at least `prerelease: true`) so they never reach a real install; `f` specifically marks a build kept around only because its CI run failed, for debugging that failure, not for retrying as-is.
